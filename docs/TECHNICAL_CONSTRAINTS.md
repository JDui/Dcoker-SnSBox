# 技术约束手册

日期：2026-11-15。本文为设计约束；现已开始实施，实际实现和验证以 EXECUTION_STATUS.md 及前后端实施记录为准。

## 1. 技术栈与组件边界

| 层 | 基线方案 | 约束 |
| --- | --- | --- |
| 主服务 | Rust stable、Tokio、Axum、Serde、tracing | 用成熟库完成 HTTP、并发、序列化与日志，不自制基础框架 |
| 自有存储 | SQLite、SQLx、显式迁移 | 初期单实例、单用户多平台账号；不提前引入 Redis、Kafka 或分布式数据库 |
| 前端 | React、TypeScript、Vite、Tailwind CSS、shadcn/ui、Lucide | 静态产物由 Rust 或同源反向代理托管；运行时无需 Node 服务 |
| 前端数据 | TanStack Query；长列表优先评估 TanStack Virtual | 服务端状态与本地草稿分开；优先成熟分页与虚拟列表实现 |
| 通信 | JSON HTTP API + SSE | SSE 用于下行事件；发送走命令接口。确有双向低延迟需求再引入 WebSocket |
| 外部接入 | 独立适配器，必要时侧车进程或容器 | 外部后端可以非 Rust；上游私有模型不得直接穿透产品 API |
| 部署 | Docker Compose；Linux amd64 优先，arm64 后续验证 | 可运行与已验收架构分别标记；不把多架构编译当作真实接入验收 |

实施时确定并锁定工具链、依赖和上游版本，提交 Cargo.lock 与前端锁文件。当前不凭空填写版本号。协议侧不自动追随 latest；一次只升级一个关键接入组件。

参考：[Axum](https://docs.rs/axum/latest/axum/)、[Vite](https://vite.dev/guide/)、[shadcn/ui](https://ui.shadcn.com/docs)、[SQLx](https://github.com/launchbadge/sqlx)、[TanStack Query](https://tanstack.com/query/latest)。

## 2. 建议模块（实现时按规模合并）

```text
crates/domain/          统一身份、消息、能力与错误模型
crates/server/          HTTP、鉴权、SSE、应用生命周期
crates/storage/         SQLite、迁移、事件与任务持久化
crates/adapter-core/    适配器契约和能力协商
crates/adapter-wechat/  微信接口映射
crates/adapter-qq/      QQ 接口映射
web/                   响应式聊天前端
deploy/                Docker 与运行示例
```

模块边界先逻辑划分；不为了目录完整提前拆出大量空 crate。适配器、存储与业务逻辑可独立测试，外部进程失效不应拖垮聚合服务。

## 3. 统一数据模型

- 身份键包含 `platform + account_id + upstream_id`；上游 ID 一律按不透明字符串处理，避免 JavaScript 大整数精度损失。
- 会话区分私聊、群聊和系统会话；保留平台归属，不自动跨平台合并联系人。
- 消息包含来源 ID、会话、发送者、平台时间、接收时间、方向、消息段和能力相关状态。平台时间缺失时显式标记，不制造可靠排序假象。
- 消息段支持文字、图片、文件、语音、视频、引用、提及和未知类型；未知消息保留类型提示，不默默删除。
- 媒体记录区分未下载、下载中、可用、过期、失败和不支持。缓存索引不代表附件已存在。
- 本地未读与平台已读分开；不支持同步已读时只能调整 SnSBox 本地状态。
- 外部 XML / HTML / 卡片作为不可信数据解析和净化，禁止直接插入 DOM 执行。

## 4. 适配器契约与能力

适配器至少描述账号状态、能力集、会话分页、历史分页、事件来源、文本发送和发送结果查询。媒体、撤回、引用、@、已读、搜索均是独立能力，允许账号或会话级别差异。

能力状态必须能区分：支持、不支持、尚未验证、暂时不可用。前端根据能力展示操作，不以按钮可点击推断后端支持。

上游错误转换为可理解的错误类别，同时在脱敏诊断中保留原因。扫码过期、账号掉线、上游拒绝、数据布局不支持和接口超时不可混为“网络异常”。

## 5. 同步、去重与恢复

- 每个账号独立维护上游游标和本地事件序号；数据库变更与可重放事件尽量在同一事务中持久化。
- 使用上游稳定消息 ID 及账号/会话作用域去重，不依赖全文哈希。没有稳定 ID 时记录降级策略和误判边界。
- SSE 支持断线后的游标恢复；事件保留窗口过期时明确要求重新获取快照，不能悄悄漏掉中间事件。
- 应用重启不得丢弃未决发送任务；上游超时也不能无限自动重发。
- 设计接受事件重复投递并幂等处理，不承诺跨进程、跨平台的 exactly-once。
- 外部资料读取考虑数据库及 WAL 的一致性，优先上游支持的快照或导出方式；不能直接复制正在写入的主数据库文件并假定完整。

## 6. 发送状态与幂等

建议状态：`queued → submitting → accepted`，或进入 `failed / uncertain`。对端投递、已读只有获得相应上游证据时才额外展示。

前端提交携带幂等键，后端在网络调用前持久化任务；同一键绑定账号、会话与原请求，参数变更应拒绝。适配器有上游幂等能力时继续传递；没有时不得在崩溃恢复后盲目重试。

`accepted` 仅说明上游接受，不能显示为对端已收到。结果不确定时展示待确认并优先查询状态；用户主动重发须能理解重复发送的可能。

## 7. 资料与访问安全

- SnSBox 自有数据库、媒体缓存与官方客户端资料分目录。默认只读接入外部资料；需要写回或接管时必须作为明确独立模式。
- 同一份官方资料目录只允许一个写入方。候选要求官方客户端退出时必须遵守；不得并行挂载同一目录给两个写入进程。
- 登录令牌和资料密钥留在服务端，不能进入前端构建产物、URL、日志或 Git。
- 初期采用单管理员会话；随机初始凭据、登录限速、HttpOnly 会话 Cookie，HTTPS 下使用 Secure；修改状态的接口校验来源并防 CSRF。
- 浏览器只访问聚合 API，不直连外部适配器管理接口。侧车 API 默认仅内部网络可达。
- 媒体下载做账号级授权和路径边界校验；不能把整个持久卷作为静态目录公开。处理上游资源 URL 时限制协议、目标及重定向，避免任意内网请求。
- 日志默认只记录事件类型、状态、耗时和脱敏标识；不记录消息正文、二维码、完整联系人或附件内容。
- 缓存容量、清理和备份保留可配置；不得以清缓存名义删除源资料。没有实现加密存储时明确说明，不能声称数据已加密。

## 8. Docker 与运行约束

- 采用多阶段构建，非 root 运行，配置与数据持久化；不默认要求 GPU、特权容器或挂载 Docker socket。
- 上游需要桌面/X11 时只放在对应侧车，不把串流编码链路重新带回主服务。
- 健康检查区分进程存活、服务就绪和账号在线；账号掉线不能简单等同容器死亡并无限重启。
- 收消息要求适配器持续运行；空闲时可以减少界面刷新，不能暂停消息进程后宣称实时在线。
- 迁移前备份，自有数据库与媒体采用一致性备份策略。回滚镜像不保证能回滚数据库；降级不兼容时通过已验证备份恢复。
- 上游进程内存和媒体解码开销计入部署资源。资源目标须经 NAS 实测，不预先承诺低至某个内存或 CPU 数值。

## 9. 最少必要验证

| 变更 | 优先验证 |
| --- | --- |
| 规划文档 | 相对链接、目标一致性、差异与敏感数据检查 |
| 适配器首次接入 | 指定版本的会话读取、一次文本收发、一次冷启动恢复 |
| 发送/同步逻辑 | 重复请求、断线或超时产生的不确定结果、重放去重 |
| 输入交互 | 中文 composition、Enter 顺序、切换会话后草稿归属；涉及 iPad 时补真机验收 |
| 部署和迁移 | 目标架构启动、持久化、备份恢复与账号状态区分 |

对当前主要风险做针对性检查。检查通过后不无故重复；只有新变更或失败证据才扩大验证。避免 SHA 文件校验及与当前问题无关的大规模测试。
