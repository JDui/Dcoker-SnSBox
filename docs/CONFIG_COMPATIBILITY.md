# wechat-selkies config 兼容计划

## 目标和证据

来源：[JDui/wechat-selkies](https://github.com/JDui/wechat-selkies)。2026-11-15 对本机对应源码只读核对：README 的持久化/下载目录说明、root/scripts/stable-desktop-environment.py、root/scripts/container_download.py。未读取用户聊天内容或令牌。

WS 把用户目录持久化到 `/config`。现有源码引用以下布局；它们是需要保全和检测的路径，不是所有版本都必定存在的文件格式合同。

| 路径 | 处理 |
| --- | --- |
| `/config/.xwechat` | 微信资料候选；保留原文件与权限，不能假定可直接读取 |
| `/config/xwechat_files` | 微信账号/历史/媒体候选；版本及数据库可读性另验 |
| `/config/.config/QQ` | QQ 官方客户端资料；附件常见在 `nt_qq_*/nt_data` 下，独立协议 token 不保证可复用 |
| `/config/.system-identity` | WS 系统身份持久化；完整保留，不在新容器生成后覆盖原身份 |
| `/config/state`、`logs`、`uploads`、桌面及下载目录 | 保留 WS 配置及用户文件，不作为 SnSBox 自有数据库目录 |

## 共用方式

**默认：原 config 只读挂载，自有状态独立挂载。** WS 可以继续作为原资料的唯一写入方。SnSBox 只读探测目录，不自动递归改权限、不尝试修复数据库、不向原目录写入索引。只有存在经过验证的接口或一致性读取方式，才声明支持历史读取。

**未来接管：先停止原资料写入方，创建一致性备份，再交给一个经过验证的适配器写入。** 在官方程序、候选协议后端之间切换前先验证版本、身份材料和回滚方式。容器内部的独占锁不能防止不遵守该锁的 WS 写入，因此不能把锁存在当作安全接管证明。

不把正在写入的数据库单文件拷贝称为备份；需要客户端停止、数据库备份接口或包含 WAL 等状态的一致性快照。SnSBox 不自动清理原始资料。

## 分层验收

1. 路径兼容：不重排现有 config，能识别候选布局；合成目录可验证。
2. 数据保全：源卷只读、自有写入在独立卷、无全目录静态暴露；隔离容器可验证。
3. 历史读取：指定客户端版本、加密格式及适配器，核对分页、附件和已知历史范围；需要授权样本。
4. 令牌恢复：指定后端实际冷启动恢复，退出后能返回原 WS；需要测试账号，不能由目录识别推断。
5. 双项目日常使用：明确只能一个官方资料写入方；若真实上游不能复用现有 token，保持原 config 完整并独立登录，不能宣称无缝共用完成。

浏览器和日志只暴露必要状态，不返回源资料文件内容、完整账号路径或登录秘密。

## 本轮活跃源只读核对

用户明确现有 WS 仍在使用，只能只读检查。用户给出的目录是 Compose 项目根，实际资料在其 `config/` 子目录。只读核对确认 `.xwechat`、`xwechat_files`、`.config/QQ`、`.system-identity` 和 `.xwechat/net/host` 存在；Compose 镜像标签为 `wechat-selkies:1.83`，该标签不等于微信/QQ 客户端的版本号。

仅检查代表性文件的 16 字节格式头，不输出原始字节：微信 session、contact、message 数据库均不具有明文 SQLite 文件头，不能按普通 SQLite 文件直接查询；未提取密钥、登录令牌或消息。QQ 存在 `nt_qq_*` 下的 `nt_data` 和 `nt_db`。报告不记录实际账号目录名。源目录未修改、未复制、未停止写入方。

固定版 Agent WeChat 的 [CLI 说明](https://github.com/thisnick/agent-wechat/blob/ce5c0687c0e99e3f93fd85266baa3fad26d63a11/packages/native-client-rust/CLI.md) 明确 `auth login --official` 是原位接管且允许写入，不是只读导入；其 [迁移说明](https://github.com/thisnick/agent-wechat/blob/ce5c0687c0e99e3f93fd85266baa3fad26d63a11/docs/src/content/docs/setup/migrate.mdx) 要求停止原客户端并备份，回退需恢复备份，不能直接把旧客户端指向 native 修改后的资料。

因此本轮不能把活跃源注册为 official profile，也不能以读权限检查通过承诺登录令牌可直接共用。允许先完成无写入的布局/格式诊断、隔离上游运行和登录操作接口。后续迁移须使用用户另行提供的一致性副本或源端一致性快照；不把运行中数据库的普通文件复制标成一致性备份。

## 第三轮：独立历史读取能力

已加入固定 `wechat-profile 2.5.0` 读取器，针对受支持的独立加密资料副本及明文兼容导出建立 SnSBox 私有索引，提供会话、分页与文字搜索。配置来源与活跃源、整个自有 data 路径隔离；系统临时目录不能位于源资料中，误配置在创建索引前拒绝。原库只作为文件读取；SQLite/WAL 恢复只发生在读取器的临时副本。

主线程的聚焦测试验证了合成加密资料、明文 WAL、源文件内容不变、分页搜索、跨来源拒绝、刷新代次以及更换来源后旧索引不复用。独立审查未发现该 reader 调用登录/联网/原位写入路径。原资料仍要求受保护且稳定的独立副本，路径检查不能代替文件系统快照或防止外部进程恶意替换目录。

当前用户没有一致性副本和数据库密钥，因此真实 WS 加密聊天仍未读到；官方 QQNT 历史解密仍不支持。读取功能不复用登录令牌，也不改变官方客户端资料所有权。部署步骤及有限覆盖范围见 [历史读取说明](../deploy/HISTORY_SETUP.md)。
